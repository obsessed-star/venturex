# Architecture

## Boundaries

`VentureEngine` owns accounts, startups, orders, trades and the seeded random generator. It exposes the same API to the browser and to Node's test runner. `app.js` renders that state and sends explicit commands to the engine; the DOM is not a financial source of truth.

The static frontend can be served by any HTTP server. `serve.cjs` is a development convenience, not an application backend. `bundle.cjs` embeds the same source files into one HTML document for offline use.

## Units and accounting

Money is stored as integer kuruş and share quantities as whole numbers. Input validation rejects unsafe integers and operations that would overdraw cash, shares or the remaining campaign allocation.

Funding debits the investor, credits the company and issues new shares. Ownership is always calculated against the updated total share count. Campaigns use flexible funding: companies can use capital before reaching the target; the model does not automatically refund an incomplete campaign.

Secondary execution transfers cash between the buyer and seller. It changes neither company cash nor total issued shares. A better-priced order executes first; at the same price, the older order has priority. The resting order sets the execution price.

Open limit buys reserve their remaining cash requirement. Limit sells reserve their remaining shares. Partial execution reduces those reservations; cancellation releases the balance. Accounts cannot match with their own orders.

Operating revenue and expenses are recorded as flows between the simulated companies and the outside economy. This distinction lets the audit reconcile total cash without pretending that the investor/company system is closed to business activity.

## One simulation day

A day updates company operating metrics and cash, processes simulated events and investor decisions, and records resulting order executions. Funding affects growth capacity and expenses. Bankruptcy halts trading and clears open orders for the company.

The random generator is seeded. Replaying the same initial state and commands yields the same result, which makes economic regression tests reproducible. Prices and chart volume come from executed trades; a day without a trade does not invent a new price.

## Price history

The chart aggregates executions into open, high, low, close and volume records. The initial 60-day history is generated by a preparation run of the same model. The displayed last price is a historical execution, not an executable quote for every quantity.

Market orders require sufficient counterparty liquidity for the requested quantity. If that check fails, the operation is rejected atomically. Limit orders may remain open or partially filled.

## Saves

The browser stores a serialized state in local storage and offers JSON export/import. Loading follows this sequence:

1. Read and parse the candidate without changing the current engine.
2. Validate its schema, supported version and economic consistency.
3. Restore a separate engine and run its accounting audit.
4. Replace the active engine only after those checks pass.

The compatibility fixture covers the previous save version. No migration silently resets an existing portfolio. A failed import preserves the current state; the UI reports the error.

## Interface

`exportJSON()` serializes a temporary state wrapper directly, avoiding the JSON clone required by the public, detached `serialize()` API. Autosave and download use this path; state validation still runs on import. Rendering updates shared summary values and only the active workspace. View navigation always renders from the current engine, so hidden panels do not need updates on each simulation tick.

The funding workspace uses one comparison list and one investment form for the selected startup. The capital trace and campaign rows share the same selection. The secondary market has a separate order ticket to keep funding distinct from investor-to-investor transfers.

SVG charts support pointer inspection and keyboard navigation. Native buttons, inputs and dialogs provide keyboard behavior; selection controls expose `aria-pressed`, and dialogs use their heading as an accessible name. Responsive layouts keep the same operations available on smaller screens.

## Verification scope

Engine tests exercise cash and share conservation, order reservations, price-time priority, invalid command rejection, funding dilution, bankruptcy, save compatibility, deterministic replay and a 365-day stress run. Browser checks cover funding, selling, pending-order cancellation, campaign filters, keyboard chart inspection and JSON save round trips.

These checks establish consistency of the implemented model. They do not validate its assumptions against actual startup returns or market behavior.
